## Phase A — Permission Registry (packages/core)
1. `packages/core/src/permissions.ts` mới:
   - Type `Permission` = string dạng `module.resource.action` (vd `accounting.payment.create`, `crm.deal.move`, `hr.attendance.checkin`, `om.wallet.spend`, `core.user.role_change`, `core.audit.read`).
   - `PERMISSION_REGISTRY`: danh sách permission có metadata { key, module, resource, action, description (tiếng Việt), securityLevel: 1|2, sensitive: boolean }. Sensitive/level-2: chi tiền (acc.create_payment, om spend lớn), đổi role, hủy voucher, xóa dữ liệu.
   - `ROLE_PERMISSIONS`: map role → permission set (owner = tất cả trong org; manager = nghiệp vụ CRUD nhưng KHÔNG role_change/không hủy voucher; staff = read + tạo nhẹ như checkin, add_contact; super_admin = wildcard). Hỗ trợ wildcard `module.*` và `*`.
   - `hasPermission(role, perm)`, `requiredSecurityLevel(perm)` helpers, pure functions, unit-test được.
2. Middleware mới `requirePermission(perm)` trong services/api/src/auth/middleware.ts: dùng SAU requireAuth — check hasPermission(role, perm) → 403 tiếng Việt kèm mã PERMISSION_DENIED + perm key; check securityLevel user ≥ requiredSecurityLevel(perm) → 403 SECURITY_LEVEL_REQUIRED kèm hướng dẫn bind email/phone (giữ nguyên format lỗi VN như gate cũ).
3. Refactor các gate hardcode hiện có sang registry NHƯNG GIỮ NGUYÊN hành vi (om/spend>1000 lớp 2, role change owner+lớp 2, hủy voucher lớp 2) — test v7a-p1/p6 hiện có PHẢI vẫn xanh không sửa assertion (nếu buộc sửa phải ghi rõ lý do vào STATE).
4. Endpoint `GET /api/v1/permissions` (requireAuth): trả registry + permissions của user hiện tại (role-resolved) + securityLevel — cho FE/AI biết được phép làm gì.
5. Unit test mới `permissions.test.ts` (core) + API test (registry đủ, staff bị 403 đúng perm, manager không đổi role được, wildcard đúng, security level gate đúng).

## Phase B — Tiểu Tâm action layer: permission + securityLevel + dry-run
1. Mỗi TieuTamAction thêm `permission: Permission` + `securityLevel: 1|2` + `sensitive: boolean` (map: acc.* tạo chứng từ = sensitive lớp theo quy tắc hiện hành; om.balance/report.summary = read lớp 1).
2. executeAction: TRƯỚC khi execute → check module active (giữ) + hasPermission(user role từ ctx) + securityLevel — thiếu → ActionResult ok:false message tiếng Việt rõ ràng (không throw 500). TieuTamActionCtx thêm role + securityLevel (lấy từ JWT/user thật ở routes).
3. DRY-RUN: executeAction(ctx, name, params, { dryRun?: boolean }):
   - dryRun=true → KHÔNG ghi DB, trả preview: { ok:true, dryRun:true, action, module, preview: mô tả tiếng Việt việc SẼ làm + params đã parse + cảnh báo nếu sensitive }.
   - Action sensitive (tạo phiếu thu/chi/hóa đơn, adjust_qty âm lớn...) → lượt ĐẦU tự động chạy dry-run trả preview + hỏi xác nhận; user xác nhận (message "đồng ý/ok/xác nhận/chốt" hoặc FE gửi confirm=true) → chạy thật. Guard chống lặp action R7.6 (system note đã-thực-hiện) phải còn hoạt động — không được double-execute sau confirm.
   - Audit ghi cả dry-run (`tieu_tam.action_dryrun`) lẫn thật (`tieu_tam.action`).
4. Chat routes (services/api/src/tieu-tam/routes.ts + adapters): wire flow confirm — state pending action per conversation (đơn giản: trả kèm pendingAction trong response/SSE, FE gửi lại confirm; hoặc lưu tt_soul_state/pending jsonb — chọn cách bền, ghi rõ vào STATE).
5. Test mới v8_5.test.ts: staff gọi action bị cấm → từ chối VN + audit; dry-run không ghi DB (đếm rows trước/sau); sensitive flow: lượt 1 preview, confirm → tạo thật đúng 1 lần; không confirm → không tạo; cross-org vẫn chặn.
